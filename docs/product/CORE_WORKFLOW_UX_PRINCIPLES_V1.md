# Core Workflow UX Principles v1

Status: Sprint 2.0 definition

Purpose:

Define interaction principles before UI design.

## Principles

### 1. Capture Should Be Faster Than Organizing

The owner should be able to preserve reality before classifying it.

### 2. Unknown Is Allowed

Unknown classification, deadline, boundary, and next movement are acceptable states of knowledge.

### 3. Classification Can Happen Later

Capture does not need to become Project immediately.

### 4. Do Not Require Metadata Without Immediate Value

Ask only for information that helps current reality, next movement, or blocker/dependency.

### 5. Never Guilt the Owner

Stale captures and waiting Projects should not be framed as failure.

### 6. Project Creation Is Deliberate but Lightweight

Project creation should require owner confirmation, name, boundary, and source evidence.

It should not require full ontology entry.

### 7. Current Reality Matters More Than Percentage Complete

JenOS should show what is true, not fake progress metrics.

### 8. Show Why Something Is Blocked

If movement is blocked, show:

- what is needed,
- who controls it,
- what scope is affected,
- what can still continue.

### 9. Do Not Equate Activity with Progress

Lots of actions do not mean the Project is healthier.

### 10. Completion Requires Owner Judgment

Submission, outcome, and acceptance are evidence, not universal completion triggers.

### 11. Maintenance Must Be Cheaper Than Decision Burden

JenOS should reduce cognitive load more than it creates system upkeep.

### 12. No Full Ontology UI

Users should not manage Person, Area, Role, Resource, Document, Event, and Decision forms before the workflow proves they are needed.

## UX Anti-Patterns

Avoid:

- inbox-like pile with no review path,
- task-list pressure,
- forced priority score,
- mandatory project setup wizard,
- dashboard before data has meaning,
- AI-looking certainty without evidence.
