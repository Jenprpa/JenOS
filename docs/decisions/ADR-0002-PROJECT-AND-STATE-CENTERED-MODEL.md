# ADR-0002: ใช้ Project และ State เป็นศูนย์กลาง แทน Task

## Status

Proposed

## Context

ชีวิตของผู้ใช้ประกอบด้วยหลายเรื่องที่เดินพร้อมกัน เช่น งานครู โครงงานนักเรียน เอกสาร การเงิน สุขภาพ บ้าน และความสัมพันธ์

แต่ละเรื่องไม่ได้มีเพียงงานที่ต้องทำ มีทั้งสถานะปัจจุบัน สิ่งที่รอ ความเสี่ยง เหตุผลของการตัดสินใจ และความทรงจำจากอดีต

หากใช้ Task เป็นศูนย์กลาง ระบบจะมีแนวโน้มลดทุกอย่างเหลือรายการงาน และทำให้บริบทสำคัญหายไป

## Decision

JenOS จะใช้ **Project** และ **State** เป็นศูนย์กลางของ Domain Model แทน Task

Task หรือ Action จะถูกมองเป็นสิ่งที่ช่วยขยับ Project จาก State หนึ่งไปยัง State ถัดไป หรือช่วยคลี่คลาย Blocker/Waiting

## Rationale

Project ทำให้ระบบมีบริบท

State ทำให้ระบบเห็นความจริงของสถานการณ์

เมื่อ Project และ State เป็นศูนย์กลาง ระบบสามารถอธิบายได้ว่า:

- เรื่องนี้อยู่ตรงไหน
- ทำไมยังไม่เดิน
- สิ่งใดควรขยับ
- สิ่งใดกำลังรอ
- สิ่งใดเสี่ยง
- สิ่งใดควรวางไว้ก่อน

## Consequences

ผลที่ตามมา:

- Core Concepts ต้องจัดรอบ Project และ State
- Today ต้องเลือกสิ่งที่ควรสนใจจาก State, Risk, Waiting, Energy และ Context
- Task list แบบรวมศูนย์จะไม่ใช่ประสบการณ์หลัก
- State Change ต้องมี History และ Source
- Waiting ต้องมี Reason และ Review Date

## Risks

- หาก State ซับซ้อนเกินไป ผู้ใช้อาจรู้สึกว่าต้องดูแลระบบมากขึ้น
- หาก Action ไม่ชัดพอ ระบบอาจช่วยตัดสินใจแต่ไม่ช่วยให้เกิดการขยับ
- หาก Project ถูกตั้งใหญ่เกินไป ระบบอาจไม่เห็น Next Action ที่จับต้องได้

## Alternatives Considered

### Task-centered Model

ปฏิเสธ เพราะขัดกับหลัก Life is not a To-do List และทำให้บริบทหาย

### Calendar-centered Model

ปฏิเสธ เพราะเวลาเป็นข้อจำกัดสำคัญ แต่ไม่ใช่แกนทั้งหมดของการตัดสินใจ

### Document-centered Model

ปฏิเสธ เพราะเอกสารเป็น Resource ไม่ใช่สถานะของชีวิตและโครงการทั้งหมด

## Open Questions

- Project ควรมี State เดียวหรือหลาย State ตามมิติ?
- Action ควรถูกสร้างจาก State โดยระบบเสนอ หรือผู้ใช้สร้างเอง?
- State taxonomy ควรเริ่มจากชุดเล็กแค่ไหน?
